# biz-db-mcp：接入 UPRC 智能体平台的改造需求

日期：2026-10-25。提出方：UPRC 智能体平台（`pi-enterprise-sandbox`）。
平台侧的通用规范见该仓库 `docs/mcp-server-guide.md`（下称“规范”），本文只列本服务需要做的改动。
与本仓库 `docs/remediation-plan.md`（下称“加固方案”）的关系在各条中注明。

## 背景与目标

业务痛点：**智能体在沙箱里生成的结果数据（清洗、汇总后的表格）需要写入业务数据库**；
反方向是把查询结果导出给沙箱继续分析。

平台的方向（规范 §6）：

- 沙箱不对外开放任何新能力。本服务**不调用沙箱接口、不持有沙箱凭据**。
- 文件进出都由平台 Agent 服务端搬运：
  - 写库：模型把文件提交为产物（不可变快照，带 `sha256`），平台取出字节，以 base64 填进本服务的导入工具。
  - 导出：本服务把文件作为 MCP `resource` 返回，由平台写进会话工作区。
- 机构号由平台按登录用户注入（规范 §3 宿主参数），模型看不到、也改不了。

平台侧的“产物参数”和“文件回传”尚在规划中；本服务先按下文准备好接口形状，平台上线后只需改配置。

## 需求清单

优先级：**P0** 接入前必须完成；**P1** 产物写库/导出功能需要；**P2** 建议。

### R1（P0）Streamable HTTP 部署形态

平台 Agent 镜像里没有 Python，生产只能以 HTTP 方式连接；当前 `main()` 只支持 stdio。

- 增加 `--transport streamable-http`、可配置 `--host`/`--port`，端点路径 `/mcp`。
- `/mcp` 校验 `Authorization: Bearer <token>`，token 来自环境变量，常量时间比较；未配置 token 时拒绝启动。
- 建议无状态模式（`stateless_http=True`），便于多副本与后续统一 MCP 网关。
  加固方案 §五 的进程级并发/限流在多副本时不是全局限额，部署说明里需写明每实例预算。

平台配置示例：

```json
{
  "id": "bizdb",
  "url": "https://bizdb-mcp.internal.example/mcp",
  "authTokenRef": "BIZDB_MCP_TOKEN",
  "timeoutMs": 180000,
  "hostArguments": {
    "instituteid": { "description": "调用者机构号", "source": "user.instituteId" }
  }
}
```

### R2（P0）`instituteid` 适配平台的宿主参数

加固方案 §五 已确定 `instituteid` 契约，与平台机制一致。落地时注意：

1. 所有工具（含将来的写入/导入工具）都有**顶层**、**必填**、`str` 类型的 `instituteid`。
   平台对必填的宿主参数缺值时会直接隐藏工具，并会删除模型传入的同名值再填入平台的值。
2. **机构号格式归一**：平台下发的是 UAuth 机构号**原值**，形如 `0800001000`（`08` 长度位 + `00001000` 机构码），
   个别用户可能没有长度位。请在解析权限前按平台同一规则归一为机构码：
   全是数字、长度 ≥ 3、前两位 L ≥ 1 且总长恰好 2 + L → 取后 L 位；否则原样。
   `institution_scopes` 配置与业务表 `ins_id_cd` 列都按机构码比较；
   如果业务表里存的是带长度位的原值，请在配置中显式声明，而不是两种写法混用。
3. 请与平台方用真实账号核对一次实际值，并在验收中覆盖“带长度位 / 不带长度位”两种写法。

### R3（P1）导出改为经 MCP 返回文件，不再直推沙箱

现状：`export` 在本机生成文件后，用 `BIZDB_SANDBOX_BASE_URL` + `BIZDB_SANDBOX_API_TOKEN` 直接上传到沙箱的
`/sessions/:sessionId/datasets`，归属身份来自进程环境变量 `BIZDB_SESSION_ID` / `BIZDB_ORG_ID` / `BIZDB_USER_ID`。
这与平台方向冲突：

- 本服务需要持有沙箱服务间凭据，沙箱对外暴露面变大，与“沙箱不新增暴露”相悖；
- 平台对所有用户共用一个 MCP 连接，进程级环境变量无法表示“当前是哪个会话”，
  共享进程下导出会写进错误的会话（加固方案 §五“查询身份与导出目标的区别”已指出）。

改为：

- `export` 不再调用沙箱。生成文件后作为 embedded resource 返回：
  `{"type":"resource","resource":{"uri":"bizdb://export/<export_id>/<filename>","mimeType":"...","blob":"<base64>"}}`，
  并附一段 `text`（文件名、行数、格式、`sha256`、是否截断）。
- 文件超过内联上限（建议 20 MiB，可配置）时，改为返回 `resource_link`，`uri` 为**本服务同源**的
  短时效一次性下载地址（签名 token，几分钟有效，下载后删除）；平台只从同源地址下载、不跟随跳转。
- 删除 `sandbox_client.py` 与 `BIZDB_SANDBOX_*`、`BIZDB_SESSION_ID` / `BIZDB_ORG_ID` / `BIZDB_USER_ID` 配置；
  加固方案 §六（Sandbox Dataset 上传链路适配）随之作废，不需要实施。
- 平台侧“文件回传”上线前，导出内容在平台里只会显示为占位文本；平台部署可先不授权 `export`。

### R4（P1）新增受控的文件导入工具，承接平台产物写库

加固方案确定“本轮不开放写入”。产物写库的需求建议**不通过开放 `execute` / `execute_many`（模型手写 DML）实现**，
而是新增一个语义很窄的导入工具：由运维白名单决定能写哪张表、哪些列、什么模式，模型不写 SQL。
这也绕开了加固方案 §二 中“解析任意 DML 的目标表、跨 schema、WHERE 豁免”等难题。

工具 `import_rows`，参数全部为顶层：

| 参数 | 类型 | 说明 |
|---|---|---|
| `instituteid` | string，必填 | 平台注入（R2） |
| `database` | string，必填 | 连接 id |
| `table` | string，必填 | `schema.table`，必须在导入白名单内 |
| `file_base64` | string，必填 | 标准 base64，由平台从产物填入 |
| `filename` | string，必填 | 由平台填入 |
| `content_sha256` | string，必填 | 解码后字节的 SHA-256（小写十六进制），由平台填入 |
| `format` | `csv` / `jsonl` / `parquet` | 可省略，按扩展名推断 |
| `mode` | `insert` / `upsert` | 必须是该表白名单允许的模式 |
| `dry_run` | bool | 只做解析与校验，返回将写入的行数和问题样例，不落库 |

导入白名单（可信配置，启动加载、重启生效）示意：

```json
{
  "imports": {
    "primary:app.report_results": {
      "modes": ["insert", "upsert"],
      "key_columns": ["report_date", "branch_code"],
      "columns": ["report_date", "branch_code", "metric", "value"],
      "institution_column": "ins_id_cd",
      "max_rows": 50000
    }
  }
}
```

行为要求：

- 校验 `content_sha256`，不一致即拒绝。
- 文件列必须是白名单 `columns` 的子集，未知列拒绝；值按目标列类型校验，失败给出行号样例。
- **机构隔离**：`institution_column` 由服务端写入调用者机构码；文件里若带该列且值不同，整批拒绝
  （不能借导入写别的机构的数据）。`upsert` 只能命中本机构的行，`key_columns` 冲突落在其他机构时拒绝。
  `all` 范围的机构是否允许跨机构导入，需业务确认，默认不允许。
- 单事务、仅 InnoDB 基表、全部成功或全部回滚；超过 `max_rows` 整批拒绝，不截断写入。
- **幂等**：以 `(instituteid, database, table, content_sha256, mode)` 记导入账本，重复提交返回
  `status=duplicate`，不重复写入。平台的调用超时后不知道结果，这是避免重复写库的唯一保障。
- 返回 `status`（`imported` / `duplicate` / `dry_run`）、插入/更新行数、导入批次 ID。
- 审计只记录哈希、行数、表名和机构，不记录数据内容。
- 写入账号只授予白名单表的 `INSERT`/`UPDATE`（及 `SELECT` 用于校验），无 DDL、无其他表权限。

`execute` / `execute_many` 在平台使用的实例中保持关闭（`BIZDB_WRITE_ENABLED=false`），
平台侧也不会授权它们。

### R5（P1）执行时间与资源

- 平台单次工具调用最长 300 秒（`timeoutMs`），超时按失败处理且无法得知结果。导出与导入的服务端期限
  应小于平台配置的 `timeoutMs`（示例 180 秒），超限主动终止并清理，返回明确错误。
- 导入的文件大小上限在工具描述中写明（base64 后字节数），平台侧会按原文件大小配置更小的上限，提前拒绝。

### R6（P2）结果与错误

- 每个结果都带 `text` 内容；平台不把 `structuredContent` 给模型。查询结果按加固方案 §五 的行数/字节上限截断并标明原因。
- 错误带稳定错误码（如 `FORBIDDEN_INSTITUTION`、`TABLE_NOT_IMPORTABLE`、`CONTENT_DIGEST_MISMATCH`、`TOO_LARGE`），
  不含 DSN、口令、SQL 原文与参数。
- 跨机构访问的拒绝与“不存在”使用同一种错误。

## 联调验收（平台侧配合）

1. HTTP 端点 + Bearer：无 token 被拒，有 token 能 `tools/list`。
2. 两个不同机构的真实用户在平台对话里查询同一张表，各自只看到本机构数据；模型传入的 `instituteid` 被覆盖。
3. 导入（平台“产物参数”上线后）：`dry_run` 报告问题行；正式导入后数据可查；重复提交返回 `duplicate`；
   文件里夹带其他机构的行被整批拒绝；超过 `max_rows` 被拒且表内容不变。
4. 导出（平台“文件回传”上线后）：小文件内联、大文件下载链接两条路径，文件在沙箱工作区中可读且 `sha256` 一致。
